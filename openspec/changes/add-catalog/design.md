# Design

## Context

См. `proposal.md` — Why. Сейчас каталог есть только частично:
`Store.ListPublic` (`internal/storage/postgres/catalog.go:15`) фильтрует
`public`+`open` и делает keyset-пагинацию по `(created_at, id)`, а `noindex`
для unlisted уже отдаётся на страницах `/t/<slug>` и `/r/<id>`
(`internal/web/api/og.go:72`, `internal/web/api/og.go:339`). При этом контракт
`/catalog` (`api/openapi.yaml:560`) объявляет `sort` и `q`, которых нет в
хранилище, HTTP-маршрут не зарегистрирован, UI — заглушка
(`web/src/pages/CatalogPage.tsx:4`). Sitemap в коде отсутствует.

## Goals / Non-Goals

**Goals:**

- довести существующий `ListPublic` до контракта: `sort=new|popular` и `q`;
- добавить `GET /api/v1/catalog` и sitemap без изменения других маршрутов;
- заменить заглушку каталога рабочим экраном с пагинацией, сортировкой и
  поиском;
- сохранить текущую гарантию: unlisted не попадает в каталог, поиск и sitemap,
  а его страницы отдаются с `noindex`.

**Non-Goals:**

- не менять схему БД и применённые миграции;
- не добавлять рекомендации, лайки или другие вне-MVP возможности;
- не менять формат существующих ответов `TierlistPage`/`TierlistSummary`.

## Decisions

1. **Расширять `tierlist.PageParams`, а не вводить отдельный тип запроса.**
   `PageParams` уже используется `ListPublic` и тестами. Добавляются `Sort`
   (`new`/`popular`, пусто = `new`) и `Query` (поиск). Валидацию значений
   выполняет HTTP-слой, а хранилище трактует неизвестные значения как
   ошибку/значение по умолчанию по контракту.

2. **Курсор остаётся непрозрачным и зависит от сортировки.** Для `new`
   сохраняется текущий формат `(created_at, id)`. Для `popular` курсор
   дополнительно несёт число ответов, чтобы keyset-условие было
   `(submissions_count, created_at, id) < (...)`; старый курсор от другой
   сортировки считается некорректным (`400`). Альтернатива — offset —
   отклонена: она даёт дубли/пропуски при добавлении ответов между страницами.

3. **`popular` считается по числу ответов, как в контракте.** Используется
   коррелированный подзапрос `count(*)` по `submissions`, уже применяемый для
   `submissions_count`. Отдельная миграция не нужна для корректности; при
   необходимости ускорения позже добавляется индекс, но это вне данного
   change.

4. **Поиск — параметризованный `ILIKE` по названию и описанию.** `q`
   обрезается по границам контракта (1–100), спецсимволы `%`/`_`
   экранируются, поиск применяется после фильтра `public`+`open`+`hidden_at IS
   NULL`. Это исключает утечку unlisted и SQL-инъекции.

5. **HTTP-обработчик каталога — новый файл `internal/web/api/catalog.go`.**
   Маршрут `GET /api/v1/catalog` регистрируется в `New`
   (`internal/web/api/api.go:104`) рядом с остальными GET. Ответ повторяет
   схему `TierlistPage` (`items`, `next_cursor`) и не раскрывает unlisted.
   Ошибки курсора/параметров маппятся в `400` через существующий
   `writeServiceError`.

6. **Sitemap — отдельный публичный маршрут.** `GET /sitemap.xml` отдаёт URL
   только `public`+`open` опросов и не содержит unlisted. Если подходящих
   опросов нет, отдаётся валидный пустой `urlset`. Альтернатива — генерировать
   sitemap статически при сборке — отклонена: список опросов меняется в БД.

7. **UI каталога следует существующему паттерну feature-модуля.** Добавляется
   `web/src/features/catalog/api.ts` с типизированным вызовом
   `GET /catalog` (типы из `web/src/api/schema.d.ts`), а
   `web/src/pages/CatalogPage.tsx` показывает список, управление
   сортировкой/поиском и кнопку следующей страницы по `next_cursor`.
   Состояния загрузки, пустого результата и ошибки обязательны; тесты — на
   MSW, как в соседних feature-модулях.

## Risks / Trade-offs

- [Счётчик ответов меняется между страницами `popular`] → keyset-курсор
  фиксирует значения на момент выдачи; возможен редкий пропуск/дубль при
  одновременном ответе. Для MVP это приемлемо, offset был бы хуже.
- [Поиск `ILIKE` по описанию без индекса может быть медленным] → ограничение
  `limit` и малый MVP-объём; при росте — trigram-индекс отдельным изменением.
- [Sitemap на большом каталоге раздувается] → ограничение разумным числом URL
  и/или разбиение на несколько sitemap в будущем; текущий MVP укладывается в
  один файл.
- [Дублирование формата `TierlistSummary` на фронте и бэке] → типы берутся из
  сгенерированной схемы, а не пишутся вручную.
