# Design

## Context

Аутентификация уже есть: серверные сессии в Postgres и CSRF-токен
(`internal/auth`, `internal/web/api/auth.go`). Опросы живут в
`internal/tierlist` и `internal/storage/postgres`, публичный каталог отдаёт их
через `internal/web/api`. У опроса есть владелец (`user_id`), состояние и
ответы; фронтенд — React (`web/src`).

## Goals / Non-Goals

**Goals:**

- один владелец — один набор операций над своими опросами;
- чужой опрос неотличим от несуществующего (`404`);
- смена пароля закрывает все сессии пользователя, кроме текущей;
- существующие публичные маршруты и прохождение опроса не меняются.

**Non-Goals:**

- модерация публичных опросов и жалобы;
- восстановление пароля по ссылке (отдельная задача);
- пагинация каталога.

## Decisions

1. **Новый неймспейс `/api/v1/me/*`** для всего, что относится к текущему
   пользователю. Альтернатива — фильтр `?mine=1` у каталога — отклонена: это
   смешивает публичный и авторский контракты.
2. **Изменение/удаление — на существующем ресурсе** `PATCH/DELETE
   /api/v1/tierlists/{id}` с проверкой владельца, а не `/me/tierlists/{id}`:
   идентификатор опроса уже уникален, и так не появляется второй путь к тому же
   объекту.
3. **Проверка владельца в одном месте**: метод хранилища возвращает опрос
   только если `user_id` совпадает; обработчик не делает отдельный запрос, чтобы
   не было TOCTOU между проверкой и изменением.
4. **Смена пароля** обновляет хеш и в той же транзакции удаляет сессии
   пользователя, кроме текущей; фронтенд получает новый CSRF-токен в ответе.
5. **Агрегаты списка** считаются запросом с `GROUP BY` по опросам автора
   (число ответов и состояния), а не N+1 запросами на каждый элемент.

## Risks / Trade-offs

- Удаление опроса необратимо: в интерфейсе нужно подтверждение, в API —
  явный `DELETE`, без «мягкого» флага. Если понадобится корзина, это отдельное
  требование.
- Смена пароля закрывает сессии других устройств: это ожидаемо, но может
  выглядеть как «разлогин»; в ответе явно сообщаем число закрытых сессий.
- Агрегаты в списке усложняют запрос; при росте числа опросов потребуется
  индекс по `(user_id, created_at)`.
