# Spec Delta

## Purpose

Восстановить в capability `accounts` проверенные аудитом TIERL-55 требования
R1–R11: серверные сессии, защищённую cookie, CSRF, выход, смену пароля,
одноразовые токены, письмо и подтверждение email, повторную отправку и запрет
создания опроса без подтверждённого email. В базе постановки живая спека
`accounts` отсутствует, поэтому требования добавляются через ADDED и получают
полную цепочку «цель → спека → код».

## ADDED Requirements

### Requirement: Серверные сессии в Postgres

Система SHALL хранить сессии на сервере в Postgres. В cookie MUST находиться
случайный токен, а в базе MUST храниться только его SHA-256. Неизвестная или
просроченная сессия MUST считаться неаутентифицированной.

#### Scenario: Вход открывает серверную сессию

- **WHEN** пользователь успешно входит с правильными email и паролем
- **THEN** сервер создаёт сессию в Postgres и возвращает cookie с токеном
- **AND** по этому токену `GET /api/v1/auth/me` отвечает `200`

#### Scenario: В базе нет рабочего токена

- **WHEN** сессия сохранена в Postgres
- **THEN** в строке сессии хранится SHA-256 токена, а не сам токен из cookie

#### Scenario: Просроченная сессия не действует

- **WHEN** срок сессии истёк
- **THEN** запрос с её cookie получает `401`

### Requirement: Защищённая cookie сессии

Cookie `tierl_session` MUST иметь `HttpOnly`, `SameSite=Lax` и `Path=/`; для
HTTPS-запроса она MUST иметь `Secure`. Выход MUST очищать cookie.

#### Scenario: Cookie входа защищена

- **WHEN** сервер устанавливает cookie сессии при входе по HTTPS
- **THEN** cookie содержит `HttpOnly`, `Secure` и `SameSite=Lax`

#### Scenario: Выход очищает cookie

- **WHEN** пользователь выходит из текущей сессии
- **THEN** сервер удаляет сессию и очищает cookie `tierl_session`

### Requirement: CSRF-токен на изменяющих запросах

Система SHALL требовать валидный `X-CSRF-Token` на запросах `POST`, `PUT`,
`PATCH` и `DELETE`. Без заголовка или с неверным токеном ответ MUST быть `403`
с кодом `csrf_failed`. Токен SHALL выдавать `GET /api/v1/csrf` и
`GET /api/v1/auth/me`.

#### Scenario: Запрос без CSRF отклоняется

- **WHEN** изменяющий запрос приходит без заголовка `X-CSRF-Token`
- **THEN** ответ `403` с кодом `csrf_failed`
- **AND** обработчик запроса не выполняется

#### Scenario: Запрос с валидным CSRF проходит

- **WHEN** изменяющий запрос содержит токен из `GET /api/v1/csrf`
- **THEN** запрос обрабатывается по своему контракту

#### Scenario: Безопасный метод не требует CSRF

- **WHEN** приходит запрос `GET` без заголовка `X-CSRF-Token`
- **THEN** CSRF-проверка не применяется

### Requirement: Выход из текущей сессии и со всех устройств

Система SHALL закрывать текущую сессию по `POST /api/v1/auth/logout` и все
сессии пользователя по `POST /api/v1/auth/logout-all`. После выхода прежняя
cookie MUST NOT давать доступ.

#### Scenario: Выход закрывает только текущую сессию

- **WHEN** пользователь выходит из одной из своих сессий
- **THEN** эта сессия больше не действует
- **AND** другие сессии пользователя продолжают работать

#### Scenario: Выход со всех устройств закрывает все сессии

- **WHEN** пользователь запрашивает выход со всех устройств
- **THEN** все сессии этого пользователя больше не действуют

### Requirement: Смена пароля инвалидирует прежние сессии

После успешной смены пароля сессии, выданные до неё, MUST перестать
действовать. При смене через `/api/v1/me/password` текущая сессия MUST
сохраниться в соответствии со спекой `author-profile`. Слабый новый пароль MUST
отклоняться без изменения пароля и сессий.

#### Scenario: Старая сессия не работает после смены пароля

- **WHEN** пользователь меняет пароль и пытается использовать ранее выданную сессию
- **THEN** запрос с этой сессией получает `401`
- **AND** вход со старым паролем отклоняется `401`

#### Scenario: Сброс пароля по ссылке закрывает все сессии

- **WHEN** пользователь устанавливает новый пароль по одноразовому токену
- **THEN** все сессии пользователя перестают действовать

#### Scenario: Текущая сессия профиля остаётся рабочей

- **WHEN** автор меняет пароль через `/api/v1/me/password`
- **THEN** текущая сессия продолжает работать
- **AND** остальные сессии пользователя закрыты

#### Scenario: Слабый пароль не меняет состояние

- **WHEN** новый пароль короче минимальной длины
- **THEN** ответ `400` с причиной
- **AND** пароль и сессии остаются прежними

### Requirement: Одноразовые токены email и сброса пароля

Подтверждение email и сброс пароля SHALL использовать одноразовый токен из 32
байт; в базе MUST храниться только SHA-256 токена, а срок действия MUST быть
ограничен. Повторная выдача токена MUST инвалидировать предыдущий, а
использованный или просроченный токен MUST отклоняться.

#### Scenario: Токен одноразовый

- **WHEN** пользователь использует ссылку подтверждения email или сброса пароля
- **THEN** повторное использование того же токена отклоняется

#### Scenario: Новая ссылка отменяет старую

- **WHEN** пользователь запрашивает новую ссылку того же назначения
- **THEN** предыдущая ещё не использованная ссылка перестаёт работать

### Requirement: Письмо подтверждения при регистрации

Система SHALL отправлять письмо со ссылкой на подтверждение после успешной
регистрации. Отправка MUST использовать SMTP (локально — Mailpit) и шаблоны
писем на ru и en. Сбой доставки MUST NOT отменять создание аккаунта и MUST NOT
раскрывать токен или ссылку в логах.

#### Scenario: Регистрация отправляет письмо

- **WHEN** пользователь успешно регистрируется с корректным email
- **THEN** аккаунт создаётся с `email_verified = false`
- **AND** на указанный адрес отправляется письмо со ссылкой `/verify-email?token=...`

#### Scenario: Сбой доставки не отменяет регистрацию

- **WHEN** SMTP-сервер недоступен во время отправки письма
- **THEN** регистрация всё равно завершается успешно
- **AND** ошибка доставки логируется без токена и ссылки
- **AND** пользователь может запросить письмо повторно

### Requirement: Одноразовый токен подтверждения email

Токен подтверждения SHALL состоять из 32 случайных байт. В базе данных MUST
храниться только SHA-256 токена, а не сам токен. Срок действия токена MUST
быть ограничен: по контракту он действует 24 часа. Использованный,
просроченный или неизвестный токен MUST отклоняться.

#### Scenario: В базе нет рабочего токена

- **WHEN** выпущен токен подтверждения email
- **THEN** в `one_time_tokens` сохраняется SHA-256 токена
- **AND** сырое значение токена есть только в ссылке письма

#### Scenario: Просроченный токен отклоняется

- **WHEN** пользователь открывает ссылку после истечения срока действия
- **THEN** ответ `400` с кодом `invalid_token`
- **AND** `email_verified` не меняется

#### Scenario: Использованный токен отклоняется

- **WHEN** пользователь повторно открывает уже использованную ссылку
- **THEN** ответ `400` с кодом `invalid_token`

### Requirement: Подтверждение email по ссылке

Система SHALL принимать токен через `POST /api/v1/auth/verify-email` и при
успехе MUST помечать email подтверждённым. Интерфейс `/verify-email` SHALL
показывать результат подтверждения.

#### Scenario: Успешное подтверждение

- **WHEN** пользователь открывает действующую ссылку из письма
- **THEN** токен используется один раз
- **AND** `email_verified` становится `true`
- **AND** интерфейс сообщает, что email подтверждён

#### Scenario: Неверная ссылка видна пользователю

- **WHEN** в ссылке нет токена или токен недействителен
- **THEN** интерфейс показывает сообщение об ошибке
- **AND** не выдаёт ошибку за успешное подтверждение

### Requirement: Повторная отправка подтверждения

Система SHALL предоставлять `POST /api/v1/auth/resend-verification` для
повторной отправки письма. Для корректного email ответ MUST быть `202`
независимо от того, существует адрес или уже подтверждён. Новая выдача токена
MUST инвалидировать предыдущую неиспользованную ссылку, а частые запросы MUST
ограничиваться rate limiting.

#### Scenario: Новая ссылка отменяет старую

- **WHEN** пользователь запрашивает письмо подтверждения повторно
- **THEN** отправляется новая ссылка
- **AND** предыдущая неиспользованная ссылка больше не работает

#### Scenario: Существование адреса не раскрывается

- **WHEN** запрос повторной отправки приходит для неизвестного или уже
  подтверждённого email
- **THEN** ответ `202` такой же, как для существующего неподтверждённого адреса
- **AND** письмо не отправляется

### Requirement: Создание опроса требует подтверждённого email

Система MUST разрешать `POST /api/v1/tierlists` только пользователю с
подтверждённым email. Без подтверждения запрос MUST завершаться `403` с кодом
`email_not_verified`.

#### Scenario: Без подтверждения создание запрещено

- **WHEN** пользователь с `email_verified = false` отправляет `POST /api/v1/tierlists`
- **THEN** ответ `403` с кодом `email_not_verified`
- **AND** опрос не создаётся

#### Scenario: После подтверждения создание разрешено

- **WHEN** пользователь подтвердил email и отправляет корректный `POST /api/v1/tierlists`
- **THEN** ответ `201` и опрос создан
