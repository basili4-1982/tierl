# Design

## Context

Создание опроса уже работает: `internal/web/api/tierlists.go:createTierlist`
принимает `POST /api/v1/tierlists`, проверяет пользователя и картинки, затем
вызывает `internal/tierlist/service.go:Create`. Сервис требует подтверждённый
email, строит тиры и элементы через `buildStructure`, валидирует их доменом
(`internal/domain/tierlist.go:ValidateStructure`) и сохраняет через
`internal/storage/postgres/tierlists.go:Create` в одной транзакции с тирами и
элементами.

Публикация: `domain.NewTierlist` проверяет видимость и slug; для `unlisted`
генерирует случайный slug через `domain.GenerateSlug` (24 символа из
`crypto/rand.Reader`), для `public` требует slug автора. Уникальность
обеспечена `tierlists_slug_key`; коллизия превращается в `409 slug_taken`.
`Service.Create` сразу переводит созданный опрос в `open` через `Publish`, то
есть отдельного шага публикации в API нет — это существующее поведение,
которое и фиксирует спека.

Редактирование: `Service.Update` меняет название, описание и видимость всегда,
а `changeStructure` проверяет число ответов и запрещает менять тиры/элементы
после первого ответа (`domain.ErrStructureLocked` -> `409 tierlist_locked`).
Хранилище повторно проверяет это под `FOR UPDATE` в
`internal/storage/postgres/tierlists.go:Update`.

Жизненный цикл: `Service.Close` идемпотентно закрывает опрос; переоткрытие
идёт через `PATCH` со статусом `open` или `public`
(`internal/web/api/tierlists.go:parseStatus`), удаление — через
`Service.Delete` и `DeleteForOwner`; ответы, тиры и элементы удаляются
каскадом по внешним ключам. Проверка владельца находится в `Service.owned`:
гость получает `403`, чужой опрос — `404`.

Требования зафиксированы в `docs/SPEC.md` §1–§3 и §11,
`api/openapi.yaml` и ADR-004, но канонической capability `tierlists` в
OpenSpec нет. Живая `author-profile` уже содержит закрытие, переоткрытие и
удаление, поэтому R3 пересекается с ней; это осознанное пересечение, а не
дублирование кода.

## Goals / Non-Goals

**Goals:**

- зафиксировать создание, редактирование и публикацию опроса как требования
  `tierlists`;
- связать требования с существующими маршрутами, доменом, сервисом,
  хранилищем, миграциями, UI и тестами;
- сохранить уже описанный в `author-profile` жизненный цикл без изменения
  поведения;
- вынести два замечания (контракт и `closed_at`) в follow-up-задачи.

**Non-Goals:**

- менять `Service.Create`, `Update`, `Close`, `Delete`, маршруты, схему БД или
  applied-миграции;
- вводить отдельный draft-эндпоинт или менять момент публикации;
- переписывать `author-profile`, `catalog`, `reports`, `submissions` или
  `item-images`;
- исправлять контракт и `closed_at` в этом change (только задачи).

## Decisions

1. **Capability `tierlists` по существующему якорю.** Имя взято из списка
   целей и не переименовывается. Оно описывает именно автора и его опрос:
   создание, публикацию, редактирование и жизненный цикл.
2. **Создание через API сразу публикует опрос.** Отдельного draft-эндпоинта в
   контракте нет; `draft` остаётся внутренним состоянием домена до вызова
   `Publish`. Спека фиксирует наблюдаемое поведение: успешное создание даёт
   `open`-опрос с выбранной видимостью.
3. **Slug — часть публикации, а не отдельная сущность.** Public требует slug
   автора (3..64, `[A-Za-z0-9_-]`) и уникальность; unlisted всегда получает
   случайный slug не короче 12 символов. Смена видимости следует этим же
   правилам: короткий public-slug при переходе в unlisted заменяется, длинный
   unlisted-slug при переходе в public сохраняется.
4. **Редактирование делится на текст и структуру.** Название, описание и
   видимость меняются всегда; тиры и элементы — только пока нет ответов.
   Это соответствует SPEC §3 и `domain.ErrStructureLocked`.
5. **Жизненный цикл R3 пересекается с `author-profile`.** В `tierlists`
   требование восстанавливается как часть способности, но источником истины
   для управления из профиля остаётся `author-profile`; маршруты
   `PATCH/DELETE /tierlists/{id}` и их проверка владельца не меняются.
6. **Замечания не меняют вердикт `ok`.** `TierlistPatch` не описывает
   `status`, хотя обработчик его принимает; `closed_at` выводится из
   `UpdatedAt` и может смещаться при правке текста закрытого опроса. Оба
   пункта вынесены в `tasks.md`, потому что код и контракт в границах аудита
   не меняются.

## Risks / Trade-offs

- [Создание и публикация не разделены] → это существующее поведение и
  контракт; отдельный draft-сценарий не требуется R1–R3 и не вводится.
- [R3 дублируется в двух capability] → `tierlists` описывает способность
  целиком, `author-profile` — авторский экран; поведение одно, дублирования
  кода нет.
- [Контракт не содержит `status` в `TierlistPatch`] → переоткрытие работает,
  но клиенту по контракту не видно; follow-up в `tasks.md`.
- [`closed_at` может смещаться] → остаточный риск корректности метаданных;
  follow-up на отдельное поле или фиксацию времени закрытия и тест.
- [Applied-миграции нельзя менять] → change только документационный,
  миграции `20261022100000`–`20261022100200` остаются без правок.

## Migration Plan

Изменение не требует миграции данных. После архивации требования попадут в
`openspec/specs/tierlists/spec.md`; откат — удаление нового change до
архивации, поведение сервиса не меняется.
