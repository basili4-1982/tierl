# Design

## Context

Аудит `docs/audits/TIERL-47.md` сопоставил задачу TIERL-47 (PR 108) с кодом.
Заявлена проверка TT-148: воркер пула стартует без `REPO` в env, а репозиторий
получает из аренды (lease). В workspace нет воркера пула, lease-клиента и
smoke-теста TT-148; `pool-smoke.txt:1` содержит только `smoke`.

В живых спеках OpenSpec нет capability, которая описывала бы пул воркеров и
аренду репозитория. Поэтому у TT-148 нет ни требования, ни кода — это gap, а не
excess.

## Goals / Non-Goals

**Goals:**

- восстановить требование TT-148 в capability `worker-pool`;
- зафиксировать наблюдаемое поведение: воркер не требует `REPO`, репозиторий
  приходит из аренды, smoke-проверка это подтверждает;
- вынести в `tasks.md` задачи на реализацию отсутствующей проверки.

**Non-Goals:**

- менять код, тесты, контракт или applied-миграции в рамках аудита;
- удалять `pool-smoke.txt` в этом change (это делает
  `remove-pool-smoke-artifact`);
- описывать продуктовые функции tierl: аккаунты, опросы, ответы и т.п.

## Decisions

1. **Новая capability `worker-pool`.** Ни один существующий якорь не описывает
   внешний пул воркеров и аренду репозитория. `self-host` — про запуск и деплой
   самого tierl; привязка TT-148 к нему исказила бы предметную область.
   Обоснование нового имени зафиксировано в `proposal.md`.
2. **Спека описывает поведение, а не файлы.** Требование говорит о запуске
   воркера без `REPO`, получении репозитория из lease и smoke-проверке; имена
   скриптов и функций остаются деталями реализации.
3. **Реализация вынесена в задачи.** В границах аудита код не меняется;
   `tasks.md` перечисляет, что нужно добавить, чтобы требование стало живым.
4. **Маркер `pool-smoke.txt` не является реализацией.** Его удаление — отдельный
   change, чтобы excess-артефакт не подменял gap.

## Risks / Trade-offs

- [Новая capability не относится к продукту tierl] → она восстанавливает
  происхождение инфраструктурной проверки TT-148, у которой иначе нет
  «цели → спеки»; в proposal явно обосновано новое имя.
- [Реализация TT-148 может жить во внешнем harness] → change фиксирует
  требование в этом репозитории и оставляет задачу сверки с владельцем
  harness, чтобы формулировка не разошлась.
- [Спека опишет поведение, которого пока нет в коде] → это ожидаемый gap:
  задачи на реализацию вынесены в `tasks.md`, аудит не выдаёт gap за ok.

## Migration Plan

Изменение документационное, миграций не требует. После архивации требование
попадёт в `openspec/specs/worker-pool/spec.md`; откат — удалить change до
архивации, поведение сервиса не меняется.
