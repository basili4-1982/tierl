# Design

## Context

См. `proposal.md` — Why. В коде уже есть серверные сессии
(`internal/auth/session.go`, `internal/storage/postgres/sessions.go`), таблица
`sessions` (миграция `20261026120000_create_sessions`), CSRF-проверка в
`internal/web/api/api.go` и отзыв сессий при смене пароля
(`internal/auth/service.go`, `internal/storage/postgres/users.go`). OpenSpec
capability для этого поведения отсутствует, поэтому аудит восстанавливает
требования, а не переписывает реализацию.

## Goals / Non-Goals

**Goals:**

- зафиксировать действующее поведение сессий, cookie, CSRF и смены пароля как
  требования OpenSpec;
- сохранить совместимость с `docs/SPEC.md`, `ADR-003` и `api/openapi.yaml`;
- подтвердить существующими тестами, что код соответствует восстановленной
  спеке.

**Non-Goals:**

- менять схему БД или applied-миграции;
- менять контракт `/auth/*` и `/csrf`;
- вводить новые способы аутентификации или хранение CSRF на сервере.

## Decisions

1. **Новая capability `authentication`, а не правка `author-profile`.**
   `author-profile` описывает управление профилем и своим опросом; сессии и
   CSRF — самостоятельное поведение аккаунта. Это позволяет позже добавлять
   регистрацию и восстановление пароля без раздувания `author-profile`.
2. **Спека фиксирует наблюдаемое поведение, а не пакеты.** Требования
   ссылаются на HTTP-маршруты, cookie и коды ответов; имена `internal/auth` и
   SQL остаются деталями реализации.
3. **Смена пароля описана через два сценария.** `/auth/change-password` и
   сброс по токену закрывают все сессии; `/me/password` сохраняет текущую —
   это уже закреплено в `author-profile`, поэтому здесь только ссылка на неё.
4. **CSRF остаётся stateless.** Токен — nonce с HMAC; сервер не хранит его в
   БД. Это соответствует контракту и не требует миграции.
5. **Код не удаляется.** Происхождение подтверждено `docs/SPEC.md` (раздел 6),
   `ADR-003` и `openapi.yaml`; избыточных реализаций в границах аудита нет.

## Risks / Trade-offs

- [Дублирование требования о смене пароля с `author-profile`] → в новой
  capability оставлена ссылка на `author-profile`, без переопределения
  поведения текущей сессии.
- [Расхождение спеки и кода при будущих изменениях] → требования привязаны к
  наблюдаемым сценариям, а `go test ./...` проверяет основные из них.
- [Applied-миграции нельзя менять] → изменение только документационное,
  `20261026120000_create_sessions` остаётся без правок.

## Migration Plan

Изменение не требует миграции данных. После архивации требования попадут в
`openspec/specs/authentication/spec.md`; откат — удаление новой capability до
архивации, поведение сервиса не меняется.
