# Design

## Context

Страница профиля уже работает: маршрут `/profile` защищён `RequireAuth`
(`web/src/routes.tsx`), страница вызывает `GET /api/v1/me/tierlists`,
`PATCH/DELETE /api/v1/tierlists/{id}` и `POST /api/v1/me/password`
(`web/src/features/profile`). Поведение API описано в
`openspec/specs/author-profile/spec.md`, а UI — только в proposal и tasks
архивного change `add-profile-views`. Поэтому аудит восстанавливает требование
к интерфейсу, а не переписывает реализацию.

## Goals / Non-Goals

**Goals:**

- зафиксировать страницу `/profile` и её действия как требование OpenSpec;
- связать UI с уже существующими требованиями к API и смене пароля;
- подтвердить существующими фронтенд-тестами, что код соответствует спеке.

**Non-Goals:**

- менять HTTP-маршруты, ответы API или схему БД;
- менять applied-миграции;
- добавлять новые возможности профиля, которых нет в TIERL-15.

## Decisions

1. **Дополняется `author-profile`, а не создаётся новая capability.** Страница
   профиля — часть той же авторской работы, что список и управление опросами;
   отдельная capability раздробила бы одно требование.
2. **Спека описывает наблюдаемое поведение, а не компоненты.** Требование
   ссылается на маршрут `/profile`, видимые данные и действия; имена
   `ProfilePage`, React Query и CSS остаются деталями реализации.
3. **Код не удаляется.** Происхождение страницы подтверждено proposal и tasks
   `add-profile-views`, а поведение — тестами `ProfilePage.test.tsx`;
   избыточных маршрутов в границах аудита нет.
4. **API-требования не дублируются.** Список, управление и смена пароля уже
   покрыты `author-profile`; новое требование только связывает их с UI.

## Risks / Trade-offs

- [Дублирование части API-сценариев в UI-требовании] → сценарии страницы
  проверяют отображение и вызовы, а правила доступа и коды ошибок остаются в
  существующих требованиях.
- [Расхождение UI и API при будущих изменениях] → требование привязано к
  наблюдаемым действиям, а `ProfilePage.test.tsx` проверяет основной поток.

## Migration Plan

Изменение только документационное. После архивации требование попадёт в
`openspec/specs/author-profile/spec.md`; откат — удаление change до архивации,
поведение сервиса не меняется.
