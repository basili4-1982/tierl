# Спецификация tierl

Документ фиксирует требования и границы MVP. Решения с обоснованием вынесены в ADR (`docs/adr/`). План работ — в issue #27.

## 1. Продукт

tierl — сервис тир-листов. Автор создаёт опрос: набор элементов и набор тиров (например S/A/B/C/D). Участники раскладывают элементы по тирам. После ответа участник видит, какая доля других участников разложила элементы похоже на него.

Сценарий:

1. Автор входит в аккаунт, создаёт опрос, публикует его.
2. Автор делится ссылкой (или опрос попадает в каталог).
3. Участник открывает ссылку, раскладывает элементы и отправляет ответ. Вход не нужен.
4. Участник видит результат: «думают как ты» и распределение по элементам.

## 2. Роли

| Роль | Что может |
|---|---|
| Гость | Открыть публичный или unlisted опрос по ссылке, ответить, увидеть свой результат, открыть каталог |
| Пользователь | Всё, что гость; после подтверждения email — создавать опросы, управлять своими опросами, видеть их статистику |
| Модератор | Скрывать опросы по жалобам (волна G) |

## 3. Опрос

- Поля: название, описание (необязательно), элементы, тиры, видимость, статус.
- Видимость:
  - `public` — виден в каталоге, индексируется;
  - `unlisted` — доступен только по ссылке; не попадает в каталог и sitemap, отдаётся с `noindex`.
- Идентификатор unlisted-опроса — криптостойкий токен (slug) не короче 12 символов. Перебор slug недопустим.
- Статус: `draft`, `open`, `closed`, `hidden` (скрыт модерацией). Ответы принимаются только в `open`.
- После первого ответа состав элементов и тиров не редактируется. Название и описание можно менять; опрос можно закрыть или удалить.
- Границы (значения уточняются в `internal/domain`, источник истины — константы там):
  - элементов: от 3 до 50;
  - тиров: от 2 до 10;
  - название: до 120 символов, название элемента — до 80, описание — до 1000;
  - у каждого тира и элемента уникальная позиция.
- Элемент: название и, опционально, картинка (волна F).

## 4. Ответ

- Ответ — отображение «элемент -> тир». Допускается неполный ответ: элементы, которые участник не разместил, считаются пропущенными и в сравнении не участвуют.
- Минимальная полнота ответа — не менее 3 размещённых элементов (иначе сходство статистически бессмысленно).
- Один ответ на анонимную сессию на опрос. Повторная отправка заменяет ответ или отклоняется — решение фиксируется в контракте (`api/openapi.yaml`).
- Ответы анонимны: в публичной статистике нет ни идентификаторов, ни email, ни IP. Автор опроса видит агрегаты, а не отдельных людей. См. ADR-002.

## 5. Метрика сходства

Подробности и обоснование: ADR-001. Здесь — нормативное определение.

Пусть ответы A и B заданы позициями тиров `ta(i)`, `tb(i)` (целые от 0 до T-1, T — число тиров), `I` — элементы, размещённые в обоих ответах, `N = |I|`.

```
similarity(A, B) = 1 - sum_{i in I} |ta(i) - tb(i)| / (N * (T - 1))
```

Свойства: значение в [0, 1]; симметрично; идентичные ответы дают 1; при `I` пустом сходство не определено, пара исключается из подсчёта. Минимальный размер пересечения для учёта пары — `min_overlap` (по умолчанию 3).

«Думают как ты» для ответа участника P:

```
share(P) = |{Q != P : similarity(P, Q) >= threshold}| / |{Q != P : similarity определено}|
```

- `threshold` — по умолчанию 0.80, настраивается в конфиге сервера.
- Если ответов в опросе меньше `min_answers` (по умолчанию 20), вместо процента показывается «мало данных». Число и порог возвращает API, чтобы интерфейс не дублировал логику.
- Дополнительно: распределение ответов по тирам для каждого элемента; наиболее и наименее похожие участники в виде агрегатов (без идентификации).

## 6. Аккаунты и безопасность

- Регистрация по email и паролю. Пароль 10–128 символов, хранится как argon2id. Email приводится к нижнему регистру, уникален.
- Создавать опросы можно только с подтверждённым email. Подтверждение и сброс пароля — по одноразовой ссылке из письма (токен 32 байта, в БД хэш, TTL: подтверждение 24 ч, сброс 1 ч).
- Сессии серверные (Postgres), cookie `HttpOnly; Secure; SameSite=Lax`, CSRF-токен на изменяющих запросах. После смены пароля все сессии сбрасываются.
- Rate limiting на вход, регистрацию, сброс, создание опросов и отправку ответов. IP хранится только как хэш с солью.
- Подробности: ADR-002, ADR-003, `SECURITY.md`.

## 7. Каталог и шеринг

- Каталог показывает только `public` и `open`; пагинация, сортировка по новизне и популярности, поиск.
- Страницы `/t/<slug>` (опрос) и `/r/<id>` (результат) отдают OG- и Twitter-теги, картинка результата — PNG 1200x630, рендерится на сервере (ADR-004).
- Жалобы на публичные опросы; скрытие по порогу жалоб.

## 8. Архитектура

Go JSON API + React SPA, статика встроена в бинарник; Postgres; SMTP (Mailpit локально); хранилище картинок — S3-совместимое или локальная FS. См. ADR-004.

Слои бэкенда: `domain` (без HTTP/SQL), `similarity` (чистые функции), репозитории Postgres, сервисы, HTTP-хендлеры. Контракт API — `api/openapi.yaml`.

## 9. Нефункциональные требования

- Тесты: ядро (`domain`, `similarity`, auth-сервисы) покрыто на 95% и выше, `go test -race ./...` зелёный.
- Линтеры и `govulncheck` проходят в CI.
- Все локали UI: ru и en; письма — ru и en.
- Запуск одной командой: `docker compose up`, проверка — `GET /healthz` отвечает 200.
- Миграции применяются автоматически при старте или явной командой; имена по timestamp.

## 10. Вне MVP

- Вход через соцсети и 2FA.
- Комментарии, лайки, подписки.
- Командные аккаунты и совместное редактирование опроса.
- Нативные мобильные приложения.
- Редактирование состава опроса после первого ответа.
- Рекомендательные алгоритмы в каталоге.
- Монетизация.

## 11. Критерии готовности MVP

- Автор проходит путь регистрация -> подтверждение email -> создание -> шеринг без ручных действий в БД.
- Гость отвечает без регистрации и видит результат.
- Unlisted-опрос не находится ни через каталог, ни через sitemap, ни через поиск (покрыто тестом).
- Все пункты разделов 5 и 6 покрыты автоматическими тестами.
